## 实测发现并修复的问题

初次回归复现了历史失败记录的误用：旧 `world-state.json` 的 `state: failed` 会让新的 `up` 提前抛出旧错误，而新的 Java 已经在后台启动。修复为每次启动生成 `launchId`，开始时写入本次“启动中”，只接受同一启动标识的成功或失败记录。Supervisor 也即时观察 Java 退出，坏 jar 可以及时报告。

原始失败后已通过严格归属检查正常关闭测试 Java，未按进程名称批量结束任何进程。

另一个回归补齐了慢启动状态：同一 PID、创建时间和绝对 jar 路径匹配时，即使端口尚未监听也保留“启动中”及归属；再次 `up` 等待原进程，不重复创建。关闭该状态时按同一进程身份等待退出。PID 复用或其他 jar 不会获得归属。

一次加强清理检查的重跑遇到 Windows PowerShell 5.1 的 `System.AccessViolationException`。当次依旧完成测试进程清理，错误记录保留在本地 `artifacts/world-verification-powershell-error.json`。未加入推测性系统修复；相同测试随后完整通过。

## 重现命令

此测试需要用户已准备的本地 jar、Java 和已接受的 EULA 文件，不包含在默认 `npm test` 中：

```powershell
node scripts/verify-world.mjs --server-jar "<已有本地jar>" --java "<java.exe>" --eula "<已接受的eula.txt>"
```

添加 `--body-workflow` 执行身体编辑、试用、应用与回滚检查。可用 `--port`、`--command-port`、`--test-port` 选择其他空闲端口。脚本拒绝占用端口，测试数据保留在 `.dev` 便于复查。最终 JSON 证据写入本地 `artifacts/world-verification.json`；这些运行文件不进入公开包。

本次证明本地离线服务端与真实 mineflayer 身体的生命周期、编辑/试用/应用/回滚，以及正式应用故障时的自动恢复闭环；未验证 Microsoft 账号登录、远程服务端或多人体验。
